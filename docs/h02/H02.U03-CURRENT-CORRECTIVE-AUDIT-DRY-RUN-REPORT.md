### 6.2 Cómo se acumulan los permisos (runtime real)

- **INFERENCIA importante:** a diferencia de lo que sugiere la auditoría previa (multi-role accumulation), el runtime actual no combina capacidades de todos los roles asignados simultáneamente; combina el rol activo de la sesión más los grants de esa asignación. Un staff OWNER+BARBER tiene en una sesión las capacidades de un solo rol, cambiables vía `iam.contexts.switch`. Esto es CURRENT, no inferencia: código de `authorization.ts`.

| RECEPTIONIST: paquete operativo fijo + permisos adicionales opcionales | RECEPTIONIST tiene `catalog.read`, `professionals.read` + grants delegables | Coherente estructuralmente |
| No existe MANAGER | No existe | Coherente |
| No se quitan permisos esenciales individualmente | UI de TeamWorkspace permite revocar cualquier grant de recepcionista | Brecha de presentación: el UI permite quitar permisos que el producto considera esenciales |

### 6.5 Proyección Dry Run para U03 (sin rediseñar IAM)

La infraestructura actual soporta el modelo producto sin sistema genérico nuevo:

- Añadir capacidades de horario al enum de contratos (ej. `schedule.read`, `schedule.manage`, `schedule.self.read`).
- `schedule.read` → por defecto a RECEPTIONIST (lectura operativa) y BARBER (lectura propia).
- `schedule.manage` → solo OWNER por defecto; delegable a RECEPTIONIST como permiso adicional opcional (reutilizando `capability_grants` y `delegableCapabilities`).
- `schedule.self.read` → BARBER por defecto (lee propio horario).
- La autorización por `business_id` y `staff_member_id` ya está en todas las consultas; tenencia cruzada devuelve NOT_FOUND (prueba integración línea 31).

CURRENT permite esto sin nuevo sistema de IAM: es el mismo patrón que `professionals.*`.

## 14. Futuros contratos U04 / H03 (DRY RUN)

### U04 (Servicios que realiza cada integrante)

U03 existe antes que U04 (§20). Después:

```
schedule (U03)    +    service assignment (U04)
```

son **inputs independientes**. El Schedule no depende de tener Servicios. En U04, `service assignment` referenciará al integrante (StaffMember) y opcionalmente a ProfessionalProfile como referencia interna; nunca exigirá que exista un horario para asignar un servicio, ni viceversa.

### H03 (disponibilidad)

H03 consumirá del modelo U03 **solamente schedule truth** (tramos semanales por día). U03 no debe:

- materializar slots;
- consultar bookings;
- crear `available=true`;
- producir fechas concretas.

H03 será quien combine `schedule truth` + `service assignment` + `bookings` para calcular disponibilidad. El contrato U03→H03 es: entregado WeeklySchedule por integrante (día → tramos [inicio, fin)).
